# Node packages and hosts

A *node package* is a library crate of nodes. A *host* links one or more packages (and the
standard nodes) into the binary that runs process groups. The `ruro` CLI scaffolds packages
and builds hosts for them, so you do not have to write the host by hand (see
[Writing nodes](writing-nodes.md#building-a-host) for doing it manually).

> **Status:** implemented and covered by unit tests. `ruro build` compiles a host, so it
> needs a Rust toolchain on the machine that runs it.

## Creating a package

```sh
ruro new package my_nodes
cd my_nodes
cargo test
```

creates a crate with an example node and its test:

```text
my_nodes/
  Cargo.toml        depends on ruro
  ruro.toml         project manifest for `ruro build`
  src/lib.rs        mod scale; pub use scale::Scale; pub fn link() {}
  src/scale.rs      the `my_nodes/scale` node and a unit test
  .gitignore
```

By default the package depends on ruro from the checkout the `ruro` binary was built in, or
from `$RURO_PATH`, or else from the git repository. `--ruro-path <dir>` and
`--ruro-git <url>` choose explicitly; `--path <dir>` sets where the package is created.
The generated `Cargo.toml` has an empty `[workspace]` table so the package builds on its
own; remove it to make the crate a member of an enclosing workspace.

Add more nodes with:

```sh
ruro new node my_nodes/threshold        # in the package directory, or --package <dir>
```

which writes `src/threshold.rs` from the same template and declares it in `src/lib.rs`.

### Testing nodes

The generated test uses `ruro::node::testing::Harness`, which runs one node in-process:

```rust
use ruro::node::testing::Harness;
use ruro::prelude::*;
use ruro::serde_json::json;

#[test]
fn scales_samples() {
    let mut node = Harness::new("my_nodes/scale", json!({ "gain": 2.0 })).unwrap();
    node.push("input", Scalar(1.5)).unwrap();
    node.step().unwrap();
    assert_eq!(node.take::<Scalar>("output").unwrap(), [Scalar(3.0)]);
}
```

`Harness` also has `set_param`, `push_encoded`/`take_encoded` (raw bytes, as they cross
processes) and `port_type`. The first `step` calls the node's `start`. Inputs queue up to
64 messages.

## `ruro.toml`

```toml
[project]
name = "my_robot"

# Where the ruro crates come from: path, git (+ branch, tag or rev) or version.
[ruro]
path = "/home/me/src/ruro"

# Packages to link into the host, keyed by crate name. Each takes path, git (+ branch,
# tag or rev) or version, and optionally package (the crate name, when it differs from
# the key) and features.
[packages.my_nodes]
path = "."

[packages.vision_nodes]
git = "https://example.com/vision_nodes"
tag = "v0.3.0"

[host]
name = "my-robot-host"      # default: <project>-host
```

## Building a host

```sh
ruro build                   # in the directory with ruro.toml
ruro daemon --host .ruro/host/target/release/my-robot-host
```

`ruro build` generates a host crate in `.ruro/host/` (rewritten on every build) whose
`main` links every package and then runs the standard host, so the host offers the
standard nodes plus yours. It builds it with Cargo and prints the command to start a
daemon with it. Options: `--manifest <file>` (default `ruro.toml`), `--debug` (no
optimisations), `--target-dir <dir>` (default `.ruro/host/target`), `--lockfile <file>`
(a `Cargo.lock` to start from when the host has none yet) and `--offline`.

To run the host on a robot, copy it there and point the robot's daemon at it, or upload
it from your workstation and select it per process group:

```sh
ruro deploy --to robot --host-binary .ruro/host/target/release/my-robot-host
```

```yaml
groups:
  vision: { host: my-robot-host }
```

See [Multi-machine graphs](multi-machine.md#custom-host-binaries).

## Message schemas

Every message type has a schema (its field layout) and a schema hash. Messages cross
processes in [postcard](https://docs.rs/postcard) encoding, which identifies fields by
position, so two processes must agree on the layout.

```sh
ruro schema                       # every standard type with its hash
ruro schema Pose                  # one type as JSON (std/Pose or just Pose)
ruro schema --all > schemas.json  # every type as a JSON array
ruro schema --host .ruro/host/target/release/my-robot-host --all   # types of a built host
ruro schema --python              # the ruro.msg Python dataclasses
```

`--host` runs `<host> schemas`, which hosts generated by `ruro build` and `ruro-host-py`
answer; the standard `ruro-host` does not.

`ruro schema diff old.json new.json` compares two schema files (one schema or an array
each) and exits with an error if any change is breaking:

```text
$ ruro schema diff pose-old.json pose-new.json
std/Pose: breaking (RS1_5b7b922a565aef20 -> RS1_b4a34eac15f0539b)
  breaking             covariance: field `covariance` added (postcard has no optional fields: old peers misread it)
error: breaking change in std/Pose (postcard encodes fields by position: adding, removing, reordering or retyping a field breaks existing peers)
```

Changes are classified as cosmetic, wire-compatible (for example a renamed field: same
bytes, but consumers that use names break), backward-compatible (an enum variant appended),
unknown (opaque types) or breaking. `--json` prints the report as JSON. Run it in CI
against the schemas of your last release to catch incompatible message changes.

The daemon does not compare schema hashes when it deploys a graph yet, so hosts built from
different versions of a message type are not detected at run time.

For a custom message, `#[derive(Message)]` derives the schema. Nested structs need
`#[derive(Describe)]` for their layout to appear in it; `#[message(opaque)]` leaves a type
out of schema checks.
