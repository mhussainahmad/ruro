# Machine learning and perception

`nodes/ruro-nodes-ml` provides the `ml/*` nodes and two messages. Only `ml/yolo-decode` is
in the standard `ruro-host`; the ONNX and LeRobot nodes are behind cargo features, so build
a host with them:

```sh
cargo build --release -p ruro-host --features ruro-nodes-ml/onnx,ruro-nodes-ml/lerobot
```

The messages:

- `ml/Tensor { shape: Vec<u32>, data: Vec<f32> }`, row-major.
- `ml/Detections { header, boxes: Vec<Detection { x, y, w, h, score, class_id, label }> }`,
  boxes in source-image pixels with `(x, y)` the top-left corner.

## Always built

- Image preprocessing: stretch or letterbox resize (bilinear), scaling, per-channel
  mean/std, RGB or BGR, NCHW float32, plus the mapping back to image coordinates.
- YOLO decoding for both common output layouts — v5/v7 `[1, N, 5 + C]` with objectness
  and v8/v11 `[1, 4 + C, N]` without — with class-wise non-maximum suppression.
- `ml/yolo-decode`: `ml/Tensor` (`tensor`) → `ml/Detections` (`detections`), for models
  run elsewhere. Parameters: `layout`, `confidence`, `iou`, `max_detections`, `labels`.

## ONNX Runtime (`--features ruro-nodes-ml/onnx`)

Uses the `ort` crate, which downloads a CPU build of ONNX Runtime at build time and
links it statically, which makes the host binary several tens of megabytes larger. For
NVIDIA GPUs, see [below](#onnx-runtime-on-nvidia-gpus---features-ruro-nodes-mlonnx-cuda).

- `ml/onnx`: `std/Image` (`image`) → model's first input; publishes the first output as
  `ml/Tensor` (`tensor`) and, with `postprocess: yolo`, `ml/Detections` (`detections`)
  mapped back through the letterbox. Input size comes from the model unless
  `width`/`height` are set. Other parameters: `model`, `resize`, `mean`, `std`, `bgr`,
  `yolo_layout`, `confidence`, `iou`, `max_detections`, `labels`, `threads`.
- `ml/policy`: robot policies exported to ONNX (LeRobot ACT, diffusion, ...).
  `std/JointState` (`state`, + optional `std/Image` on `image`) → `std/JointCommand`
  (`action`), 30 Hz by default. Input and output names are parameters (`state_input`,
  `image_input`, `action_output`; LeRobot naming by default: `observation.state`,
  `observation.image`; an empty `action_output` takes the first output). On an emergency
  stop it sends no actions and drops the current action chunk. Models that output an action chunk `[1, K, D]` have the chunk
  executed one action per step (or the first `actions_per_inference`) before running
  again. Optional state normalisation and action de-normalisation (`state_mean`,
  `state_std`, `action_mean`, `action_std`) for exports that leave them out.

Both are tested end to end (`tests/onnx.rs`) with two models of a few hundred bytes,
checked in under `tests/models/` and generated by `tools/make_test_models.py`: a detector whose output layout and NMS outcome
are known, and a policy returning a two-step action chunk.

Exporting a LeRobot policy to ONNX is done on the Python side (`torch.onnx.export` of
the policy's `select_action`/model forward with fixed input shapes); recurrent or
stateful samplers (diffusion denoising loops) must be exported as a single graph or
unrolled.

## LeRobot datasets (`--features ruro-nodes-ml/lerobot`)

`ml/lerobot-recorder` writes LeRobot's v2.1 dataset format:

```
meta/info.json, meta/episodes.jsonl, meta/tasks.jsonl, meta/episodes_stats.jsonl
data/chunk-000/episode_000000.parquet
```

with `observation.state`, `action`, `timestamp`, `frame_index`, `episode_index`,
`index` and `task_index` columns and per-episode statistics computed as LeRobot does.
Episodes start and stop with the `recording` input (or `auto_start` and
`episode_seconds`); recording resumes an existing dataset if its features match.
Inputs: `state`, `action`, `image`, `recording`. Parameters: `root`, `fps`, `task`,
`robot_type`, `camera` (empty: no images), `joint_names`, `auto_start`,
`episode_seconds`.

**Deviation:** camera frames are stored as PNG images inside the Parquet files
(feature dtype `image`, the Hugging Face `Image` type) rather than as MP4 videos,
because there is no pure-Rust MP4/AV1 encoder suitable here; `video_path` is null.
LeRobot v2.1 supports image features stored this way. Datasets can be converted to
video storage with LeRobot's own tools if size matters.

**Validation.** `tests/lerobot.rs` reads the files back with the Rust Parquet reader.
With `RURO_LEROBOT_PYTHON` pointing at a Python that has `datasets<=3.6`, `pandas` and
`pillow`, it also runs `tools/check_lerobot_dataset.py`, which loads the data the way
`LeRobotDataset.load_hf_dataset` does (Hugging Face `datasets`), compares the features
with the ones LeRobot derives from `info.json`, decodes the images and checks indices,
timestamps and statistics. Loading through `LeRobotDataset` itself was not tried,
because it requires PyTorch.

## ONNX Runtime on NVIDIA GPUs (`--features ruro-nodes-ml/onnx-cuda`)

`ml/onnx-cuda` runs a model with ONNX Runtime's CUDA execution provider. Its input is a
float32 `gpu/Tensor` (`tensor`), typically from `gpu/normalize` (see
[GPU buffers](gpu.md)); a tensor in device memory is handed to ONNX Runtime by its device
pointer and read where it is, so images go from `gpu/upload` to the model without passing
through the host. It publishes one output (`output_name`, default the first) as an
`ml/Tensor` (`output`) in host memory, for `ml/yolo-decode` and other CPU nodes. Other
parameters: `model`, `device` (CUDA ordinal), `input_name` (default the first input), and
`profile`, a path prefix for an ONNX Runtime profile (JSON, written when the node stops)
with each operator's time and the execution provider it ran on. A host tensor is accepted
too (ONNX Runtime copies it to the device).

```yaml
nodes:
  camera: { type: hw/v4l2-camera, group: cam }
  upload: { type: gpu/upload, group: cam }
  normalize: { type: gpu/normalize, group: infer, params: { width: 640, height: 640 } }
  model: { type: ml/onnx-cuda, group: infer, params: { model: yolov8n.onnx } }
  boxes: { type: ml/yolo-decode, group: infer }
wires:
  - camera.image -> upload.image
  - upload.out -> normalize.image
  - normalize.tensor -> model.tensor
  - model.output -> boxes.tensor
```

The feature downloads ONNX Runtime 1.28 with its CUDA 13 provider at build time. It needs,
at run time:

- an NVIDIA driver for CUDA 13 (R580 or newer);
- the CUDA 13 runtime (`libcudart.so.13`), cuBLAS (`libcublas.so.13`, `libcublasLt.so.13`)
  and cuRAND (`libcurand.so.10`) on the library path, and cuDNN 9 for models with
  convolutions: from the CUDA toolkit, or from pip (`nvidia-cuda-runtime==13.*`,
  `nvidia-cublas==13.*`, `nvidia-curand`, `nvidia-cudnn-cu13`) with their `lib` directories
  in `LD_LIBRARY_PATH`;
- glibc 2.38 or newer (Ubuntu 24.04, Debian 13): that ONNX Runtime build does not load, or
  link, on older systems;
- `libonnxruntime_providers_cuda.so` and `libonnxruntime_providers_shared.so` next to the
  host binary: the build copies them beside it in `target/<profile>/`, so copy them along
  when installing the host elsewhere.

Without them the node fails to start and says which library is missing.

Tested (`tests/onnx_cuda.rs`) on an RTX 4090 with driver 610.57.04 in Ubuntu 24.04, with the
pip libraries: a device tensor run in place gives the CPU's results, the node takes device
and host tensors, and ONNX Runtime's profile shows every operator of the test model on
`CUDAExecutionProvider`. CI builds and lints the feature but has no GPU to run it.
